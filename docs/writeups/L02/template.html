1. Design

We wanted a teacher or technician to be able to set the box up with nothing but a phone, and we wanted every reading to reach the cloud exactly once, even when the network is unreliable. The firmware from Level 1 keeps running. We added four parts to it, each a FreeRTOS task on core 0:

  • wifi: setup access point, joining and re-joining the network, mDNS and internet time.
  • web: serves the setup page and the local status page.
  • telem (core 1): takes one reading every 5 s.
  • uplink: sends everything to the server over HTTPS.

Readings and events do not go straight to the network. They first go into an outbox, and leave it only when the server has confirmed it holds them.

4. Problems and fixes

What went wrong in practiceWhat we changed
Every upload was refused with 401: the token had been pasted together with its T07-D1= label.Both the device and the server now drop that label, so either form works.
On the very first start the board restarted after ~40 s: formatting the 8 MB file system kept the web task away from the watchdog.The pages are installed first, and only then does the task join the watchdog.
Power-ups were logged as BROWNOUT: full Wi-Fi transmit power pulled the USB supply down.Transmit power set to 15 dBm. The hotspot still sees about −45 dBm.
OFFLINE appeared after 29 s, uncomfortably close to the 30 s limit.The device now checks in every second; the server marks it offline after 12 s of silence and checks every 2 s.
A rare start-up crash loop (tcpip_send_msg_wait_sem): the web server opened its socket before Wi-Fi had started.The web task waits until the Wi-Fi task has brought the network stack up.

5. Level 2 extra items

  • How the setup page saves the details: the network name, password, Room ID and device token are written to NVS (flash).
    • The details are marked verified once they have connected.
    • The 8-character AP password is generated once, from letters that cannot be confused with each other, and kept.
    • reset or a 5 s BOOT press clears only the Wi-Fi details.
  • Reconnection strategy:
    • New details that fail within 12 s send the device back to setup mode, with the reason on the page (wrong password / network not found).
    • Verified details never fall back to setup. The device keeps retrying with gaps of 1, 2, 4 and then 8 s, so it is back within about 15 s of the hotspot returning.
    • Level 1 keeps running the whole time.
  • mDNS: smartclass-t07.local (HTTP service), restarted on every connection.
  • Replays rejected: the table seen_seq has the primary key (device_id, seq), shared by telemetry and events.
    • A message sent twice gets HTTP 409 and is not stored again.
    • seq comes from a lease saved in NVS, so it never repeats after a restart.
  • HTTPS with the server certificate checked: WiFiClientSecure.setCACert() with a bundle of public root CAs (ISRG, Google Trust Services, DigiCert, USERTrust, Amazon). A certificate that does not chain to one of them fails the handshake. Every request carries the device token as a Bearer header.
  • No password, key or token in the repository:
    • The device token is typed on the setup page.
    • The server reads DATABASE_URL, DEVICE_TOKENS and ADMIN_PASSWORD from Render environment variables.
    • .env files are git-ignored.
